# Native GPU maximum 950 MHz experiment (A/B/A), 2026-09-25

**Result: 950MHz actually reached, GPU render time improved, but UI jank
persists. This is NOT a fully fixed stable kernel.**

User specifically requested a native GPU maximum test because 600MHz busy
boost did not make rapid drag responsiveness satisfactory. This
diagnostic applies 950MHz only to **actually busy** native GPU windows
while respecting idle and KGSL thermal limit, NOT permanent fixed 950MHz
or the unsupported historical 960/980MHz OC.

## Isolated source and images

drivers/devfreq/governor_msm_adreno_tz.c accepts optional p11.gb=600
OR p11.gb=950 (or no option for original TZ governor). Exact
seven-frequency table 950/900/820/745/600/465/320 MHz is mandatory.
Original TZ algorithm runs first. When a >=5ms sample has >=3ms
actual busy time, >=40% utilization and validated 0<total,
busy<=total (64-bit percentage math), the 600 mode requests index4,
950 mode requests native index0. If the original TZ vote is even
higher, honor it; if the GPU is idle, this policy does not intervene.
The subsequent KGSL power-level adjustment still enforces thermal,
existing constraints and normal sleep, and the native top stays 950MHz.
Potential power/heat/skin-severity and panel correctness risks remain.

color split; it cannot establish physical panel correctness.

## Outcome

**The max-clock test did NOT eliminate frame drops.**
The remaining buffer/HWC/DDR/SurfaceFlinger pipeline still incurs
delays even when GPU renders much faster. Do not treat "always
950MHz" as a production fix, overclock 960/980, or merge this
experimental mode into stable.

The device is left on p11.gb=950 via **temporary** fastboot boot
so the user can physically assess responsiveness and tint. User can
report recurrence immediately. Normal restart returns to the existing
installed boot (not necessarily the stable source release).
Private boot images and traces are not committed.
